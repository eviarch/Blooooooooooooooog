## 二、图片方案定调

**结论：仓库里只保留压缩后的 WebP，不放原始无损图。**

依据：

1. Hexo 是原样复制图片的，不做缩放或重编码，放多大就发多大；
2. CI 会把整个 `public/` 强推到 `deploy` 分支，图片体积会同时压在仓库、构建时间和流量上；
3. 瀑布流单列宽度只有 255–300px（手机 150px 基准），点击放大查看器放大的是 `img.src` 本身，1600px 边长已经足够。

压缩参数建议：最长边 1200–1600px、质量 75–85；带文字的截图/示意图用 PNG 或无损 WebP，避免有损压缩的文字色晕。

## 三、启用主题自带的 masonry 瀑布流相册

涉及三处：

1. 数据文件 `source/_data/masonry.yml`：主题的 `scripts/data-handle.js` 会把它挂到 `theme.masonry`，模板 `layout/pages/masonry/masonry.ejs` 直接对它做 `forEach`；
2. 页面文件 `source/masonry/index.md`：`front-matter` 里已有 `template: masonry`，不需要改动；
3. 导航入口 `_config.redefine.yml` 的 `navbar.links`，原先是被注释掉的模板，已启用。

踩坑记录（都实测过）：

- **`masonry.yml` 不能为空**，只剩注释也不行。YAML 解析结果是 `null`，`theme.masonry` 为 `undefined`，模板渲染抛 `Cannot read properties of undefined (reading 'forEach')`，页面产物是 **0 字节**（这就是仓库里 `/masonry/` 页一直是空文件的原因）；
- **任意一张图 404，整个瀑布流会永远停在骨架屏**。主题的 `plugins/masonry.js` 是等所有图片 `load` 完成后才初始化 MiniMasonry 布局的，少一张就永远差一个；
- **masonry 的图片不走 lazyload**。主题的懒加载过滤器只作用于文章正文（`after_post_render`），相册图片是模板直接输出的，会一次性全部加载——这也是更该用压缩 WebP 的原因；
- 点击图片会打开主题自带的图片查看器（滚轮缩放 0.8–4 倍、拖动平移、方向键切换、Esc 关闭），`imageViewer.js` 明确绑定了 `.masonry-item img`。

## 五、修复 `npm run server` 报错

现象：

```
'hexo' 不是内部或外部命令，也不是可运行的程序或批处理文件。
```

根因：这份 `node_modules` 是在 **Linux/WSL** 里安装的。`node_modules/.bin` 下 **0 个 `.cmd` / `.ps1`**，只有 Linux 符号链接，Windows 读取到的实际内容是 WSL 的链接格式：

```
hexo    -> IntxLNK ../hexo/bin/hexo
stylus  -> IntxLNK ../stylus/bin/stylus
terser  -> IntxLNK ../terser/bin/terser
```

Windows 的 cmd 无法执行这种文件，所以 npm 在 `node_modules/.bin` 里找不到 `hexo.cmd`。

处理：按 npm 在 Windows 上的标准内容补了两个启动器，指向 `..\hexo\bin\hexo`：

- `node_modules/.bin/hexo.cmd`
- `node_modules/.bin/hexo.ps1`

验证：`npm run build` 正常；`npm run server` 启动后 `/masonry/` 返回 HTTP 200。

注意：`node_modules` 被 gitignore，这个修复**不会进入版本库**，将来重新安装依赖就会消失（届时会由 npm 自动生成正确的启动器）。彻底解决方式是执行 `npm ci` 在 Windows 下重装依赖——顺带也能替换掉其中的 Linux 版原生二进制（例如 minifier 用的 jpegtran、pngquant）。
